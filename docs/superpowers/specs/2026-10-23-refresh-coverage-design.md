# Context refresh coverage

A short navigation entry can retain an old progress summary even after an authority record changes. Existing refresh_context faithfully copies startup_context into tracked host-instruction regions; it does not edit the navigation entry or understand linked records. Binding status verifies discoverability and generated bytes, not the accuracy of the author's summaries.

Expose this boundary in successful refresh and binding responses: generated_context=current; short_entry, linked_records and summary_accuracy=not_checked. This is additive reporting, not a new stale-state detector. Failed/conflicting refreshes must not claim current generated context. Existing changed lists, protected regions, custom paths, soft-budget warnings and idempotence remain intact.

Update the existing management workflow to review authority, navigation and startup source separately. Keep navigation concise and link to frequently changing progress rather than duplicating it. Only changed records are written through controlled plans. After refreshing, read back the relevant entry and authority; tool success is insufficient for semantic freshness.

Alternatives: automatic prose rewriting would destroy user ownership; mtime/hash differences cannot identify a true contradiction without declared derivation metadata. Neither is justified here. No new scan, scheduler, network request, record schema or dependency tracker. An optional explicit source-provenance feature can be evaluated separately if an actual need remains.

Synthetic regression fixtures deliberately make entry prose disagree with a work record, then verify that refresh leaves both untouched and truthfully reports unexamined scope. Custom navigation paths, successful bindings, unchanged refreshes and edited-region conflicts must retain their behavior. Public fixtures contain no field records.
